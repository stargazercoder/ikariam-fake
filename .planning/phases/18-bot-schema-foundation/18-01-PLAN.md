Create the file `supabase/migrations/20260317000001_bot_schema.sql` with the following exact SQL:

**Step 1 — ALTER profiles table to add two boolean columns:**
```sql
ALTER TABLE public.profiles
  ADD COLUMN is_bot   boolean NOT NULL DEFAULT false,
  ADD COLUMN is_admin boolean NOT NULL DEFAULT false;
```
Both columns use `NOT NULL DEFAULT false` so existing rows are backfilled automatically by PostgreSQL — no UPDATE migration needed.

**Step 2 — REVOKE client UPDATE on is_bot and is_admin columns (defense-in-depth):**
```sql
REVOKE UPDATE (is_bot, is_admin) ON public.profiles FROM authenticated;
```
This prevents any authenticated client from setting `is_bot` or `is_admin` via a Supabase client update call, even though the existing `profiles_update_own` RLS policy would allow row-level access. Column-level REVOKE is the DB-enforced protection layer.

**Step 3 — CREATE bot_schedules table:**
```sql
CREATE TABLE public.bot_schedules (
  bot_id         uuid PRIMARY KEY REFERENCES public.profiles(id) ON DELETE CASCADE,
  is_paused      boolean     NOT NULL DEFAULT false,
  aggression     integer     NOT NULL DEFAULT 1 CHECK (aggression BETWEEN 0 AND 3),
  next_action_at timestamptz NOT NULL DEFAULT NOW()
);
```
- `bot_id` is both PK and FK — one schedule per bot.
- `ON DELETE CASCADE` cleans up when a bot profile is deleted.
- `aggression` CHECK constraint enforces 0-3 range.
- `next_action_at` uses `NOT NULL DEFAULT NOW()` so newly created bots are immediately eligible for the first tick.

**Step 4 — Enable RLS with no policies (deny-all for clients):**
```sql
ALTER TABLE public.bot_schedules ENABLE ROW LEVEL SECURITY;
```
No `CREATE POLICY` statements. With RLS enabled and no matching policies, authenticated clients receive zero rows. Only SECURITY DEFINER functions (pg_cron bot tick, GodMode RPCs) bypass RLS and can read/write this table.

Add a comment block at the top of the file explaining the migration purpose. Add inline comments for each step as shown above.
