    **Migration 20260311000008_resource_production_functions.sql:**

    1. Function `public.process_resource_tick()` — SECURITY DEFINER SET search_path = ''
       - Returns void, language plpgsql
       - Iterates all city_resources rows with JOINs to city_buildings for:
         a. The production building matching the resource type:
            - wood -> no building yet (skip or use 0 production) — wood production requires a sawmill which is not in the BLDG-01 list. For v1 Phase 2: wood production rate = 0 unless a building provides it. Since town_hall is the only level-1 building, only gold produces.
            - Actually, re-reading the research more carefully: the CASE maps wood->sawmill, marble->quarry, crystal->glassblower, sulfur->sulfur_pit, gold->town_hall. These production buildings (sawmill, quarry, etc.) are NOT in the BLDG-01 building_type CHECK constraint. This means they don't exist as city_buildings rows.
            - SOLUTION: For Phase 2, the process_resource_tick function uses LEFT JOIN to city_buildings. If no matching production building exists (sawmill, quarry, etc.), the production level and workers are 0, so production for that resource type is 0. Only gold (mapped to town_hall, which exists at level 1) will actually produce.
            - This is correct behavior: in the original Ikariam, wood/luxury resources come from island-level shared resource buildings (not city buildings). Phase 3 (World Map) will add island resource areas. Phase 2 only needs Gold production to work correctly.
         b. The warehouse building for capacity calculation
       - Production formula: `workers * prod_level * 1.0` (research_bonus hardcoded to 1.0 for v1)
       - Capacity formula: `500 * POWER(1.5, warehouse_level)` (base capacity 500)
       - Update: `LEAST(current_amount + production, capacity)`
       - Only update if production > 0 (skip resources with no production building)

    2. Function `public.deduct_resource(p_city_id uuid, p_resource_type text, p_amount numeric)` — SECURITY DEFINER SET search_path = ''
       - Returns void, language plpgsql
       - Updates city_resources SET amount = amount - p_amount WHERE city_id = p_city_id AND resource_type = p_resource_type AND amount >= p_amount
       - If no rows updated (insufficient resources), RAISE EXCEPTION 'Insufficient %', p_resource_type
       - Called by the upgrade-building Edge Function (Plan 02)

    **Migration 20260311000009_construction_functions.sql:**

    Function `public.complete_building_upgrades()` — SECURITY DEFINER SET search_path = ''
    - Returns void, language plpgsql
    - Finds all construction_queue rows WHERE finish_at <= NOW()
    - For each: UPDATE city_buildings SET level = target_level, updated_at = NOW() WHERE city_id AND building_type match
    - DELETE the completed queue entry
    - Use a FOR loop over the result set (same pattern as research example)

    **Migration 20260311000010_pg_cron_jobs.sql:**
    - CREATE EXTENSION IF NOT EXISTS pg_cron WITH SCHEMA pg_catalog (idempotent)
    - GRANT USAGE ON SCHEMA cron TO postgres
    - GRANT ALL PRIVILEGES ON ALL TABLES IN SCHEMA cron TO postgres
    - Schedule resource-tick: `cron.schedule('resource-tick', '*/5 * * * *', 'SELECT public.process_resource_tick()')`
    - Schedule construction-tick: `cron.schedule('construction-tick', '* * * * *', 'SELECT public.complete_building_upgrades()')`

    CRITICAL: The pg_cron extension MUST be created in a migration file (NOT seed.sql) to avoid the "schema cron does not exist" error. See research Pitfall 1.
